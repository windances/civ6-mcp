# Civ 6 智能体在 token 上花费多少（实测，2026-09-28）

DSH 发出的每一次模型调用都会写入其会话日志，形式是一条 `assistant/chunk`，其 chunk 类型为
`usage`，因此 `.dsh-home/sessions/**/session.jsonl.zstd` 是**一份完整的账本**，而不是抽样。读取它的是
本地工具 `.tools/token-stats.mjs`（未纳入版本控制，与其同类文件 `advisor-usage.mjs`
和 `china-usage.mjs` 一样；`.tools/` 按设计被忽略）：

```
node .tools/token-stats.mjs                 # totals, roles, models, top sessions
node .tools/token-stats.mjs --tools         # + tool-call histogram and result sizes
node .tools/token-stats.mjs --per-turn      # + tokens per game turn, session by session
node .tools/token-stats.mjs --json          # machine-readable
```

## 记录的确切内容

| 字段 | 含义 |
|---|---|
| `inputTokens` | 提示中**未被缓存**的部分 |
| `cacheReadTokens` | 提示中由缓存提供的部分 |
| `outputTokens` | 生成的 token，`reasoningTokens` 是其中一个子集 |
| `totalTokens` | `input + cacheRead + output`（已用样本核对：11226 + 21120 + 58 = 32404） |

因此 **prompt tokens = input + cacheRead**，而与钱相关的划分是新鲜（fresh）与缓存（cached）之别；本文件
统计的是 token，不是货币，因为定价是提供商侧的设置。

一个游戏回合是从 `end_turn` 自身的结果开始计数的，该结果以 `Turn 60 -> 61` 开头。自上一次计数以来花费的
一切就是该回合的工作；一次返回**被阻塞**的 `end_turn` 不会推进任何东西，也不会获得任何归集桶。

## 中国对局在 T271 时的快照

114 个会话文件，其中 95 个带有 usage 记录，4,259 次模型调用，全部使用 `deepseek-official /
deepseek-v4-flash`。

| | token 数 |
|---|---|
| prompt 总计 | **911.4M**（新鲜 **6.07M** + 缓存读取 **905.4M**） |
| output 总计 | **7.01M**（推理 **5.42M**，即 77%） |
| 按 harness 的计法总计 | **918.5M** |
| 从未缓存（新鲜输入 + 输出） | **13.08M** |
| 缓存读取占 prompt 的比例 | **99.3%** |

按游戏回合平均（对整局取平均）：**8.3 次模型调用**、18.2 次工具调用、**1.78M 总 token**、
11.8k 新鲜输入、13.6k 输出（其中 10.5k 是推理）、工具结果约 22k 字符。

| 角色 | 会话数 | 调用数 | 总计 | 新鲜输入 | 输出 | 游戏回合数 |
|---|---|---|---|---|---|---|
| 驱动游戏的会话 | 39 | 3,943 | 898.9M | 5.21M | 5.67M | 515 |
| 工具/编写类会话 | 13 | 273 | 18.1M | 448.5k | 335.8k | 0 |
| 顾问子代理 | 43 | 43 | 1.44M | 412.1k | 1.00M | 0 |

顾问层只占账单的 **0.16%**：43 个会话，每个只有一次模型调用，因为这些 worker 是在不可变快照之上做
一次性 JSON 提议的，而且没有工具。

## 每回合的成本随游戏推进而增长，原因就在提示上

整局共归集到 511 个回合（在被放弃的分支里重玩过的回合会再次计入——日志记录的是已经付出的工作量，
而不是唯一回合）：

| 区间 | 回合数 | 总计/回合 | 提示/回合 | 输出/回合 | 推理/回合 | 调用/回合 |
|---|---|---|---|---|---|---|
| T1-T30 | 28 | 562.9k | 556.3k | 6.6k | 5.3k | 6.0 |
| T31-T60 | 41 | 573.2k | 563.3k | 10.0k | 8.1k | 6.0 |
| T61-T90 | 130 | 1.19M | 1.18M | 10.1k | 8.1k | 6.6 |
| T91-T120 | 116 | 1.42M | 1.42M | 6.6k | 4.6k | 5.3 |
| T121-T150 | 62 | 1.95M | 1.94M | 8.8k | 6.1k | 6.2 |
| T151-T180 | 54 | 2.42M | 2.40M | 18.0k | 13.8k | 10.8 |
| T181-T210 | 19 | 2.32M | 2.30M | 16.8k | 12.9k | 10.4 |
| T211-T240 | 30 | 2.41M | 2.40M | 11.6k | 8.6k | 8.9 |
| T241-T270 | 30 | 2.35M | 2.34M | 8.4k | 5.3k | 6.9 |

**一个回合的成本是开局三十个回合时的 4.3 倍**，而且增长完全在提示上：每回合的输出始终处在 6.6k 到 18k
之间。每次模型调用携带约 214k token 的上下文（99% 为缓存读取），而一个回合包含 6-11 次这样的调用，
所以账单是*上下文 × 步数*。

两个后果，都可供行动：

- **工具输出不是主因。** 所有工具结果加起来每回合约 22k 字符，大致是 5.5k token——约占该回合提示的
  0.3%。精简 `get_cities` 不会让这个数字变化。
- **每回合的步数才是乘数**，步与步之间常驻内容的大小同样是乘数。可用的杠杆是：减少每回合的模型调用次数
  （批量下命令，避免在拒绝之后重新读取）、更小的常驻上下文（本参考文件有 42 KB，而且每次调用都会重新
  发送），以及 `reasoningEffort`，因为推理占全部生成 token 的 77%。

## 注意事项，以免把这些数字读过头

- **缓存读取不是免费的，但也不是全价。** 918M 中有 905M 是缓存读取的 prompt；把它变成钱的是提供商的
  缓存命中率。
- **重玩会被计入。** 被放弃的分支重玩了 T61-T120（两个区间分别是 130 和 116 个回合），因此这些区间是
  “已经玩过的回合”，而不是“最终时间线的回合”。
- **有 85 次 `end_turn` 调用没有推进任何东西**（599 次调用，515 个已归集回合）：被阻塞的回合仍然要付出
  那些发现阻塞的调用的成本。
- 会话标题生成和网页搜索子请求是各自独立的事件类型；它们没有被单独计为行（约占调用的 2%，而且它们运行在
  同一个模型上）。
- 该工具会连同代码一起打印完整的方法说明，而且它的数字会随着实况对局的进行而变化——请重新运行它，而不要
  引用本文件的快照。

# 用 DeepSeek Harness 重写 Civ6 MCP

## 编排者–工作者实现与鉴定计划

本文档描述如何用 DeepSeek Harness（DSH）以编排者–工作者架构集成并逐步重构
[`civ6-mcp`](https://github.com/lmwilki/civ6-mcp)。它旨在可作为实现计划、测试计划和发布鉴定
清单重复使用。

## 1. 推荐架构

使用两个编排层：

1. 一个**开发编排者**协调实现、审查并鉴定该系统的 DeepSeek 工作者。
2. 交付的**文明玩家编排者**协调只读的专家工作者，并独占唯一一条会改变状态的执行路径。

起初不要移植 FireTuner 与生成的 Lua 实现。保留现有的 Python MCP 服务器作为环境适配器，
只有在替换代码证明行为对等时才迁移各个组件。

```text
DSH Civ Orchestrator
  |
  +-- Strategy worker
  +-- Military/map worker
  +-- Economy/city worker
  +-- Diplomacy/victory worker
  |
  +-- Plan validator and conflict resolver
  +-- Sole-writer action executor
          |
          v
  One shared civ6-mcp process
          |
          v
  Civ VI FireTuner on localhost:4318
```

### 核心安全规则

工作者只提建议；编排者行动。只有编排者/执行者才可以调用会改变状态的工具或 `end_turn`。
这可以防止并行工作者针对不断变化的游戏状态发出相互冲突的命令。

## 2. 标准鉴定模型

每个实现阶段都必须产出四类证据：

1. **产物** —— 代码、配置、schema、fixture 或报告。
2. **自动化证据** —— 具有机器可读结果的可重复测试。
3. **运行时证据** —— 来自真实会话或由 fixture 支撑的文明会话的日志。
4. **退出关卡** —— 明确的通过/失败标准。

阶段不得仅凭智能体的书面报告就宣布完成。鉴定失败会把工作退回实现阶段；后续阶段不得为一个
未鉴定的基础做补偿。

## 3. 阶段 0 —— 建立基线

### 工作

固定以下各项的确切版本或修订：

- `civ6-mcp`
- DeepSeek Harness
- Python 与 `uv`
- Node.js 与包管理器
- Civilization VI 及所需的 DLC
- 测试存档文件

创建有代表性的场景：

1. 带有单位、研究与生产的开局回合。
2. 移动与战斗。
3. 外交或一份收到的交易。
4. 一个结束回合的阻塞项。
5. 世界议会或一个后期存档。
6. 保存、重新加载与恢复。

运行原项目的单元测试，并记录其 MCP 工具清单、延迟、错误与回合行为。

### 产物

- 版本清单
- 带哈希的场景/存档清单
- 基线测试报告
- MCP 工具清单
- 基线遥测摘要

### 鉴定关卡

- 现有 Python 测试原样通过。
- 发现的 MCP 工具恰好符合预期；当前基线为 76。
- 连续十次 `get_game_overview` 调用成功。
- 代表性的单位、城市、地图、研究与外交读取成功。
- 一个无害动作被接受，并由随后的游戏状态验证。
- 至少三个回合完成，没有跳过或重复的回合。
- 记录基线延迟、错误率与 token 用量。

如果该关卡失败，先修复环境，再开始 DSH 集成。

## 4. 阶段 1 —— 安装并固定 DeepSeek Harness

### 工作

安装 DSH 及以下各项所需的组件：

- MCP 客户端连接
- 进程内派生的子智能体
- 子智能体控制
- 工作流执行
- 工作者线程工作流执行
- 结构化工作者输出
- 工具限制

把所有 `@deepseek-ai/dsh-*` 包固定到与 DSH 宿主相同的发行版。避免依赖可能解析为不兼容候选
发行版的 npm 标签。

相关的上游参考：

- [DSH 子智能体子系统](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/subagent.md)
- [DSH 工作流包](https://github.com/deepseek-ai/deepseek-harness/tree/master/packages/workflow)
- [DSH 工作流工作者](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/workflow/workflow-worker-thread/README.md)

### 产物

- 固定版本的包清单与锁文件
- DSH 组合/配置档
- 最小的并行工作者冒烟工作流
- 安装与升级说明

### 鉴定关卡

- `dsh --version` 与已安装的插件版本一致。
- DSH 启动时没有未解决的插件依赖。
- 一个父级并发启动两个工作者。
- 两个工作者都返回符合 schema 的 JSON。
- 取消操作会终止工作流及其全部子级。
- 配置的深度限制阻止工作者继续向下委派。

## 5. 阶段 2 —— 把 DSH 连接到 `civ6-mcp`

### 工作

使用官方 DSH MCP 客户端启动现有的 Python 服务器。一个起始配置是：

```yaml
- id: mcp-civ6
  name: '@deepseek-ai/dsh-mcp-client'
  config:
    serverName: civ6
    transport: stdio
    command: uv
    args:
      - run
      - --directory
      - /absolute/path/to/civ6-mcp
      - civ-mcp
    cwd: /absolute/path/to/civ6-mcp
    env:
      CIV_MCP_DISABLE_LUA: "1"
    toolCallTimeoutMs: 720000
    failOnStartupError: true
```

较长的超时是为了容纳 `end_turn`，它可能花掉几分钟等待 AI 文明。DSH 以限定名称暴露发现到的
工具，例如：

```text
mcp__civ6__get_game_overview
mcp__civ6__get_units
mcp__civ6__unit_action
mcp__civ6__end_turn
```

参考：[`@deepseek-ai/dsh-mcp-client`](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/mcp/mcp-client/README.md)。

### 产物

- DSH MCP 配置
- 工具清单比对脚本或测试
- 连接与重连测试
- DSH 到 MCP 的兼容性报告

### 鉴定关卡

- DSH 发现完整的预期工具清单。
- 输入 schema 与直接 MCP 的 schema 一致。
- 通过 DSH 的代表性调用与直接 MCP 结果一致。
- 杀掉 MCP 子进程会造成可见失败，并且重连成功。
- 重启 DSH 不会留下第二个 FireTuner 连接。
- `end_turn` 不会被 MCP 超时过早取消。
- 当 `CIV_MCP_DISABLE_LUA=1` 时，`run_lua` 不存在。

## 6. 阶段 3 —— 证明单智能体对等

### 工作

在引入工作者之前，使用仓库的 `AGENTS.md` 作战手册，让单个 DSH 智能体针对现有的 MCP 工具
运行。这样可以把集成失败与编排失败区分开。

### 产物

- 单智能体的 DSH 角色设定与指令
- 工具调用与回合日志
- 对照基线的对等性报告
- 失败分类报告

### 鉴定关卡

- 在至少两个场景中完成至少 20 个连续回合。
- 不发生重复的动作提交。
- 不发生无法解释的回合跳跃。
- 每个回合都具备全部五项必需的日记反思。
- 每个阻塞项都被解决，或以正确的下一步动作上报。
- 保存/重新加载保留游戏标识与回合数。
- 工具调用成功率至少 99%，不含预期内的游戏规则拒绝。
- 结果相对原始基线没有实质性倒退。

## 7. 阶段 4 —— 定义规范契约

定义并版本化三个 schema。

### 7.1 回合快照

```json
{
  "version": 1,
  "turn": 42,
  "gameId": "rome_123456",
  "overview": {},
  "units": [],
  "cities": [],
  "map": {},
  "diplomacy": [],
  "victory": {},
  "blockers": [],
  "recentEvents": []
}
```

### 7.2 工作者提案

```json
{
  "worker": "military",
  "assessment": "Eastern border is exposed.",
  "priority": 80,
  "actions": [
    {
      "actionId": "T42-military-001",
      "tool": "unit_action",
      "arguments": {},
      "preconditions": [],
      "expectedEffects": [],
      "risk": "medium"
    }
  ],
  "warnings": [],
  "confidence": 0.82
}
```

### 7.3 执行结果

```json
{
  "actionId": "T42-military-001",
  "status": "executed",
  "toolResult": "...",
  "verified": true,
  "observedEffects": [],
  "replanRequired": false
}
```

### 产物

- 带版本的 JSON Schema
- 带类型的表示
- 有效与无效的 fixture
- schema 迁移策略

### 鉴定关卡

- 在每个智能体边界都校验 schema。
- 缺失必填字段时按失败关闭。
- 未知的工具名称被拒绝。
- 无效坐标与过期的回合号被拒绝。
- 重复的 `actionId` 值被拒绝。
- 每个 fixture 快照往返后都不丢失信息。
- 一百个畸形提案测试不产生任何游戏变更。

## 8. 阶段 5 —— 构建只读专家工作者

### 工作者角色

| 工作者 | 职责 |
| --- | --- |
| 战略（Strategy） | 胜利路线、研究与市政，以及长期优先级 |
| 军事/地图（Military/map） | 威胁、战斗、移动与探索 |
| 经济/城市（Economy/cities） | 生产、增长、区域、建造者与开销 |
| 外交/胜利（Diplomacy/victory） | 交易、关系、宗教、议会与对手的胜利威胁 |

### 工作

编排者只采集一次快照，并把同一份不可变快照发送给每个工作者。工作者通常不应获得任何文明
MCP 工具。它们分析所提供的快照并返回结构化提案。

起初使用新的一次性工作者。如果领域专属记忆带来可度量的价值，以后再评估可续用的工作者。

配置：

- 每回合最大工作者数：4
- 最大委派深度：1
- 要求结构化输出
- 每个工作者的运行时长与 token 预算
- 最大结果大小
- 独立的超时处理

### 产物

- 四个工作者角色设定
- 工作者专属的提案 schema 或 schema 约束
- 工具限制
- 工作者单元测试与提示词注入测试

### 鉴定关卡

- 工作者看不到也无法调用变更工具。
- 每个工作者都收到相同的快照版本与回合。
- 每个被接受的工作者结果都符合 schema。
- 每个工作者都停留在其被指派的领域内。
- 重放同一快照会产生实质一致的优先级。
- 一个工作者失败不会阻塞成功的工作者。
- 工作者无法创建孙级。
- 分析阶段不发生任何游戏状态变更。

## 9. 阶段 6 —— 实现编排者

### 回合状态机

```text
OBSERVE
  -> FAN OUT
  -> COLLECT
  -> VALIDATE
  -> RESOLVE CONFLICTS
  -> BUILD ORDERED PLAN
  -> EXECUTE
  -> VERIFY
  -> REFLECT
  -> END TURN
```

对于原型，使用 DSH 的工作流设施与 `parallel()`。对于生产环境，优先使用固定的、可审查的插件
或工作流，而不是每回合生成一个新的编排脚本。

### 确定性冲突策略

1. 拒绝针对错误游戏或错误回合的提案。
2. 拒绝无效或被禁用的工具。
3. 合并相互兼容的只读建议。
4. 检测针对同一单位或城市的多个动作。
5. 强制性的阻塞项优先于可选的改进。
6. 生存类动作优先于经济优化。
7. 让编排者模型只在已校验的备选方案中做选择。
8. 产出一份串行动作清单。

### 产物

- 回合状态机
- 扇出工作流
- 提案收集器与校验器
- 确定性冲突解决器
- 冲突 fixture 与决策日志

### 鉴定关卡

- 每个编排周期恰好创建一份规范快照。
- 每回合最多运行四个工作者。
- 冲突 fixture 总是产出其预期结果。
- 同一单位不能收到两个终结性指令。
- 一个城市不能收到相互冲突的生产指令。
- 工作者失败导致降级运行，而不是不受控的重试。
- 工作流取消后不留下任何仍在运行的子级。
- 最终计划只包含白名单内的工具。

## 10. 阶段 7 —— 加入唯一写者执行器

只有执行者可以调用会改变状态的 MCP 工具。

### 执行协议

在每个动作之前：

1. 确认游戏标识。
2. 确认当前回合。
3. 检查该动作 ID 尚未执行过。
4. 重新检查相关的前置条件。
5. 执行该动作一次。
6. 查询受影响的状态。
7. 比较观察到的效果与预期的效果。
8. 继续、重新规划，或安全停止。

文明的操作通常不是幂等的。对超时的变更永远不要盲目重试。先查询状态，以判断原操作是否已经
生效。

### 产物

- 变更允许清单
- 串行化的执行队列
- 每回合动作账本
- 前置条件与后置条件检查器
- 重新规划接口

### 鉴定关卡

- 并发变更被串行化。
- 重复的动作 ID 绝不执行两次。
- 一次成功变更之后的模拟超时会被验证检测出来。
- 过期的动作被拒绝。
- 验证失败会停止依赖它的动作。
- 独立动作只有在被显式标记为安全时才继续。
- 日志把提案、MCP 请求、原始结果与验证串联起来。

## 11. 阶段 8 —— 集成结束回合处理

保留 Python 服务器的结束回合状态机。把结果当作控制信号：

| 结果 | 编排者的响应 |
| --- | --- |
| 需要生产 | 重新规划城市生产 |
| 需要研究 | 询问战略工作者 |
| 需要晋升 | 询问军事工作者 |
| 外交待处理 | 询问外交工作者 |
| 世界议会待处理 | 询问外交/胜利工作者 |
| 检测到卡死 | 允许 `civ6-mcp` 恢复 |
| 游戏结束 | 停止编排循环 |

### 鉴定场景

- 空的生产队列
- 已完成的研究
- 未移动的单位
- 有可用的总督或晋升
- 收到的外交
- 收到的交易
- 世界议会
- 正常的 AI 回合
- 被中断的 FireTuner 连接
- 自动存档恢复

### 鉴定关卡

- 每个阻塞项都路由到正确的工作者或处理器。
- 重试 `end_turn` 不会重复写入日记条目。
- 一个待处理的结束回合请求不会被发送两次。
- 回合数恰好前进一次。
- 恢复会重新加载预期的标识与回合。
- 游戏结束状态终止所有工作者。

## 12. 阶段 9 —— 加固安全与隔离

### 工作

- 禁用 `run_lua`。
- 不给予工作者任何文明变更工具。
- 强制执行执行器变更允许清单。
- 把仪表板绑定到 `127.0.0.1`，除非远程访问是有意为之。
- 让凭据远离提示词与工作者环境。
- 限制工作者数量、深度、token、运行时长与结果大小。
- 记录包版本与提示词哈希。
- 把工作者输出当作不可信数据。

### 鉴定关卡

- 工作者提示词注入测试无法调用任何文明工具。
- 无法调用任意 Lua。
- 无法通过非回环接口访问仪表板端点。
- 秘密模式扫描在日志或日记中找不到任何凭据。
- 超大与深度嵌套的提案被拒绝。
- 取消操作在限制时间内使工作者与工作流进入静止状态。

## 13. 阶段 10 —— 影子模式评估

在不执行其提案的情况下运行编排系统。把它的计划与原始单智能体的动作做比较。

### 指标

- 提案 schema 的有效性
- 相互冲突的建议
- 被漏掉的强制性阻塞项
- 战术合法性
- 战略一致性
- 分析延迟
- token 与金钱成本
- 工作者失败率

### 初始鉴定目标

- 100% 的被接受提案符合 schema。
- 零提案使用被禁用的工具。
- 零个强制性阻塞项被漏掉。
- 至少 95% 的提议动作合法。
- 解决冲突之后的冲突率低于 10%。
- 决策延迟不超过所测基线的 2 倍。
- token 成本保持在约定预算内。

只有在有实测基线证据时才能调整目标，并把理由记录在鉴定报告中。

## 14. 阶段 11 —— 受控实机评估

运行难度递增的实机评估：

1. 五回合，每次变更前都需人工批准。
2. 二十五回合，自动执行。
3. 三个固定的 50 回合场景。
4. 一局完整的游戏。
5. 多个文明与胜利策略。

### 鉴定关卡

- 零重复变更。
- 零无法解释的回合跳过。
- 至少 99% 的有效工具调用率。
- 所有注入的游戏崩溃都能从预期的存档恢复。
- 每个已执行的动作都有验证证据。
- 每个已完成的回合都有有效的日记记录。
- 在生存、扩张、产出与胜利进度方面，战略结果不差于单智能体基线。
- 额外的延迟与成本被测量并上报。

## 15. 阶段 12 —— 带后备方案的上线发布

加入一个显式的运行模式开关：

```text
CIV_AGENT_MODE=single
CIV_AGENT_MODE=orchestrated-shadow
CIV_AGENT_MODE=orchestrated-live
```

在编排实现成功完成多局完整游戏之前，保留原来的单智能体路径。

### 产物

- 模式开关与配置
- 后备流程
- 运维手册
- 发布说明与已知限制
- 最终鉴定报告

### 鉴定关卡

- 无需改代码即可切换模式。
- 同一个存档可以在单智能体模式下继续。
- 工作者系统故障会导致受控停止或按配置回退。
- 遥测能识别出每个决策由哪个模式负责。
- 发布文档记录了固定版本、安装、限制与恢复方式。

## 16. 开发编排者的工作包

DeepSeek 开发编排者应当委派有界的工作包：

| 工作者 | 工作包 |
| --- | --- |
| 集成工作者 | DSH 组合、MCP 连接、版本固定 |
| 契约工作者 | schema、角色设定、工具策略、校验 |
| 运行时工作者 | 编排、冲突解决、执行器 |
| 鉴定工作者 | fixture、故障注入、指标、报告 |

开发编排者拥有架构决策，串行地集成补丁，运行完整的鉴定套件，并拒绝缺乏测试证据的完成声明。
工作者不应成为自己所写代码的唯一审查者。

## 17. 必需的测试矩阵

| 领域 | 正常情况 | 失败情况 | 必需证据 |
| --- | --- | --- | --- |
| MCP | 发现并调用所有工具 | 服务器崩溃/重连 | 工具清单与日志 |
| 快照 | 完整一致的状态 | 字段缺失/畸形 | schema 测试报告 |
| 工作者 | 四份有效提案 | 超时、无效 JSON、提示词注入 | 工作者结果账本 |
| 冲突 | 兼容的提案合并 | 同一单位/城市被两次针对 | 确定性的 fixture 结果 |
| 执行器 | 动作成功并得到验证 | 超时、过期状态、部分生效 | 动作与验证日志 |
| 结束回合 | 恰好前进一次 | 阻塞项、外交、议会、卡死 | 回合转移日志 |
| 恢复 | 正确的自动存档被重新加载 | 标识错误或回合倒退 | 标识与回合证据 |
| 安全 | 工作者只读行为 | 尝试使用被禁用的工具与 Lua | 拒绝/审计日志 |
| 性能 | 并行分析完成 | 工作者缓慢或失败 | 延迟与成本报告 |

## 18. 完成定义

当以下全部为真时，项目即告完成：

- 一局完整的 Civilization VI 游戏通过 DSH 编排完成。
- 没有任何变更被执行两次。
- 没有任何回合被意外跳过。
- 每个动作都可从提案一路追溯到验证。
- 所有工作者边界都强制执行 schema 与工具限制。
- 注入的连接故障与游戏故障都能正确恢复。
- 日记与遥测允许重放和审计这局游戏。
- 战略结果达到或超过单智能体基线。
- 延迟与成本保持在约定限制内。
- 单智能体后备方案保持可用。
- 安装、运行、鉴定与恢复都有文档记录。

## 19. 推荐的实现顺序

依赖安全的实现顺序是：

```text
Baseline
  -> DSH installation
  -> MCP integration
  -> Single-agent parity
  -> Schemas
  -> Read-only workers
  -> Orchestrator
  -> Sole-writer executor
  -> End-turn integration
  -> Security hardening
  -> Shadow evaluation
  -> Controlled live evaluation
  -> Rollout
```

在编排系统使用现有的 Python 适配器通过实机鉴定之前，不要开始完整的 FireTuner 或 TypeScript
移植。到那时，各个适配器领域就可以在契约测试的保护下被替换，而无需同时改变智能体架构。

## 20. 已实现的里程碑（2026-09-05）

工作区现在包含一个可直接运行的里程碑 1 基础：

- 项目本地的 DeepSeek Harness `0.1.2-rc.1` 与项目本地的 `uv`；
- 上游 `civ6-mcp` 固定在提交
  `dd2019056371b92ea4854e879ddf05a8cad95e8a`；
- 一个 DSH overlay，它启动 `civ-mcp`、移除 `run_lua`、禁用通用委派路由，并提供一个受深度
  限制的无工具顾问路由；
- 四个专家提示词、三个失败关闭的 JSON Schema，以及一个唯一写者编排技能；
- 无头与网页启动命令；以及
- 静态检查、适配器单元检查、MCP 协议检查与解析配置检查。

用以下命令运行完整的免密钥鉴定关卡：

```bash
npm run qualify:all
```

该关卡按如下方式鉴定这个基础：

1. `qualify` 解析所有 schema、检查工作者提示词、确认 overlay 的安全设置，并把 MCP 清单与
   固定基线做比较。
2. `qualify:python` 从预期的 `tests/` 目录运行上游适配器回归测试。
3. `qualify:mcp` 通过 stdio 初始化真实适配器、列出工具、验证 `run_lua` 不存在，并检查所需的
   编排工具。
4. `dsh:dump` 让已安装的 DSH 二进制解析该 overlay。任何无效的组件、补丁或配置档都会使该命令
   失败。

对于实机鉴定，启动启用了 FireTuner 的 Civilization VI，导出 `DEEPSEEK_API_KEY`，然后运行：

```bash
npm run dsh:play -- "Play one complete turn using the civ6-orchestrator skill."
```

里程碑 1 不是最终的上线关卡。实机对等性、故障注入、多回合影子评估，以及对提案/动作账本的
确定性代码级强制执行，仍受上文阶段 3 至 12 的约束。

## 21. 确定性内核进展（2026-09-06）

仓库现在实现并测试了最初的代码级编排边界：

- 由 Ajv 支撑的、针对快照、工作者提案与执行结果的校验；
- 不可变的已校验输入与带类型的 TypeScript 声明；
- 每个工作者的工具/领域允许清单；
- 拒绝过期的游戏/回合数据、重复的动作 ID、缺失的单位/城市引用、无效坐标、任意 Lua 与未知
  工具；
- 确定性的动作排序与单位/城市/全局冲突解决；
- 当一个工作者返回无效提案时的降级收集；
- 每回合的 claim/result 动作账本；以及
- 一个唯一写者执行器：它串行化变更、校验标识与前置条件、验证效果、对含义不明的失败绝不盲目
  重试，并在验证失败后停止。

由 fixture 支撑的测试包括 100 个畸形提案且零变更调用、稳定的冲突结果、重复保护、串行执行、
过期状态拒绝、含义不明超时的验证，以及验证失败即停止。

直接用以下命令运行这些测试：

```bash
npm run test:orchestrator
```

阶段 4、6 和 7 已有实质推进，但在把内核接入一个固定的 DSH 工作流/插件、并针对实机工作者与
文明会话加以演练之前，尚未完全通过鉴定。
